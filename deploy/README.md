# Развертывание конвейера

## Исполнитель

Постоянного исполнителя у проекта нет. Машину сборки заводит на каждый прогон
общий оркестратор проекта: он получает вебхук о событиях конвейера, читает теги
заданий (`pipeline-$CI_PIPELINE_IID`) и регистрирует исполнителя ровно с этим
тегом, а по завершении прогона удаляет машину вместе с ним. Подключение проекта
к оркестратору — его перечень проектов и вебхук «Pipeline events» с ключом
вызова в заголовке — настраивается вне этого репозитория.

Задания идут в образе заданий проекта из своего реестра (`MFR_CI_IMAGE`): SDK
и прогретый кеш пакетов по lock-файлам. Машина при подъёме получает этот же
образ от оркестратора, поэтому задания его не качают. Без переменной задания
идут в публичном `mcr.microsoft.com/dotnet/sdk`, и прогон качает SDK и пакеты
сам.

## Образ заданий

Собирает и публикует ручное задание `image:ci`: Build → Pipelines → Run
pipeline, затем «играть» у задания. Скрипт `deploy/docker/build-ci-image.sh`
проверяет образ restore без сети и ставит две метки: версионную
`sdk10-<номер прогона>` — точку отката — и подвижную `latest`, на которую
смотрят `MFR_CI_IMAGE` и оркестратор. Откат — перестановка `latest` на прежнюю
версионную метку.

Пересобирать после смены пакетов, lock-файлов или SDK. Без пересборки прогон
не падает: недостающее restore докачивает из сети. Пересборка — решение
человека, сама она не запускается.

## Правила запуска

Прогон заводится на merge request, на `master` и вручную (Build → Pipelines →
Run pipeline). Пуш в ветку без merge request прогона не заводит. Merge request
вливается только после успешного прогона: в настройках проекта включено
«Pipelines must succeed», пропущенный прогон успехом не считается.

## Переменные конвейера

**Settings → CI/CD → Variables**:

| Переменная | Значение |
|---|---|
| `MFR_LEAK_PATTERNS` | образцы утечек через `\|` (домены провайдеров, названия хостов) — задаёт владелец |
| `MFR_LEAK_ALLOWED_PATHS` | `contract/client-api.yaml\|addresses.json` (по умолчанию) |
| `GITLAB_PUSH_TOKEN` | personal access token с `write_repository` — для `publish:tag` |
| `MFR_CI_IMAGE` | образ заданий проекта, метка `latest` |
| `MFR_CI_DOCKER_IMAGE` | образ с клиентом Docker — для `image:ci` |
| `MFR_IMAGE_REGISTRY` | префикс своего реестра со слэшем на конце |
| `MFR_REGISTRY_AUTH`, `MFR_REGISTRY_TOKEN_URL` | вход в реестр учётной записью машины (`deploy/docker/registry-login.sh`) |

## Выпуск

1. Владелец снимает суффикс: `<Version>X.Y.Z</Version>` в `Directory.Build.props`.
2. Пуш в `master` → `version` пропускает, `publish:launcher` публикует exe
   в пакет проекта, `publish:tag` ставит метку `vX.Y.Z` на этот коммит.
3. Выдача игрокам — человек загружает exe из пакета через админку основного
   репозитория; регистрация записи закрытая, перед открытием объект скачивают
   из обоих регионов раздачи и сверяют по хешу с собранным.
