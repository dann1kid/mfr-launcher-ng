# AGENTS.md — правила работы в репозитории клиента

Клиентское приложение игровой сборки Morrowind Fullrest Repack для Windows: установка и обновление
игры, линии, пакеты опций, пресеты движков, самообновление. Стек — C# на .NET 10, Avalonia, SQLite,
xUnit. Сервер, контракт, админка и конфигуратор живут в основном репозитории проекта (рабочая копия —
соседний каталог `../mfr-launcher`); здесь только клиент.

## Четыре правила, которые нельзя нарушать

### 1. Клиент — потребитель замороженного контракта

Источник правды о протоколе — контрактные артефакты основного репозитория: `client-api.yaml`
(`shared/api-client/src/main/resources/mfr/contract/`), `schema.proto` и `version.proto`
(`shared/proto/src/main/proto/mfr/contract/`). Не код клиента и не поведение клиентов, уже
установленных у игроков: разошлись клиент и контракт — неправ клиент.

- `contract/` хранит дословные копии этих файлов, `contract/SOURCE` — выпускную метку основного
  репозитория `vX.Y.Z` и SHA её коммита. Произвольный SHA не годится: клиент не опирается на поле,
  которого ещё нет в бою. Нужно новое поле или путь — правка контракта по правилам основного
  репозитория (только добавления), выпуск сервера, затем синхронизация здесь.
- Копии руками не правятся: обновление — `deploy/gitlab-ci/sync-from-main.sh <метка>` отдельным
  коммитом. Тот же скрипт приносит дословные копии общих скриптов конвейера; их тоже не правят
  здесь — правка идёт в основной репозиторий и приезжает синхронизацией.
- Классы proto генерируются из `contract/*.proto`; DTO с `contract/client-api.yaml` сверяет
  контрактный тест: обязательные поля, необязательность, пути и параметры, значения enum.
- Клиент ходит только по путям контракта. Резервных протоколов, резервных серверов и переключения
  протокола при сбое нет: сбой — это недоступный сервер, а не повод сходить в другое место.
- Незнакомое значение — штатный случай: неизвестный `compression` значит «копии нет, качаем сырой
  объект», файл с чужим `os` пропускается.

Причина: выпущенные клиенты разом не обновить, а копия, которую правят руками, отстаёт молча.

### 2. Отката нет — самообновление вперёд обязательно

Один лаунчер обслуживает все живые линии игры, а вернуть игрока на предыдущую версию лаунчера
нельзя: выпущенный дистрибутив исправляется только следующим. Поэтому:

- версия, которую открывают игрокам, сама узнаёт о следующей и ставит её. Запись дистрибутива
  не открывают, пока эта версия не умеет обновить себя: исправление до такого игрока уже не доедет;
- канал — `/v2/launcher/*` с `os=WINDOWS`. Обновление предлагается, только если версия на сервере
  строго больше своей по числовым октетам; строку, которая не разбирается, не предлагать.
  Проверка «не равно» превращает любое расхождение в бесконечное «Обновить лаунчер»;
- версия, которую клиент сообщает о себе, побайтно равна `<Version>` сборки, метке выпуска и id
  записи дистрибутива;
- каждый выпуск больше любого id, уже зарегистрированного для этой ОС: апдейтер установленного
  клиента сравнивает версии неравенством строк и встанет на меньший номер так же, как на больший;
- ревизия пути (`/v2/…`) — параметр клиента, адреса запросов собираются в одном месте
  (`ApiClientV2`). Появилась новая ревизия — в старую клиент не ходит: её значения закреплены
  для уже установленных клиентов;
- состояние клиента (`launcher.db`) меняется только миграциями вперёд: новая версия открывает базу
  любой прежней без потерь, и это проверяется тестом;
- поля `jdk` и `jdk_storage` нужны только апдейтеру установленного клиента; этот клиент —
  самодостаточный exe и их игнорирует. Дистрибутив регистрируется без архива среды исполнения:
  запись наследует среду, на которой апдейтер установленного клиента запускает переход.

### 3. Без вендоров, хостов и истории

В коде, комментариях, тестах, `docs/`, этом файле и сообщениях коммитов нет названий облачных
провайдеров, хостов и доменов серверов, идентификаторов ресурсов и отсылок к предыдущей реализации:
сопоставлений «там это называлось так», ссылок на её репозиторий, её версий как эталона. Пишем
в терминах предметной области: «сервер выдачи», «регион раздачи», «объектное хранилище»,
«клиент, уже установленный у игроков», «состояние установленного клиента».

- Адреса серверов в репозитории — только заглушки. Реальные подставляет сборка: в конвейере — из
  замаскированных переменных, локально — из `context/private/client.props`. Публикация с
  требованием адресов без них падает. `launcher.json` рядом с exe переопределяет адреса при запуске
  и в гит не попадает.
- Задание `leak-scan` ловит домены инфраструктуры и названия провайдеров в составе имён хостов,
  а не отдельные слова: название продукта, пространство имён `Com.Lezenford.Mfr.*` (выведено
  из `package` в proto, то есть часть контракта) и адрес пространства имён XAML утечкой не являются.
  Исключений по путям нет. Ссылки сообщества — содержимое продукта, собранное в одном ресурсе.
- Образцы `leak-scan` — в переменной конвейера; в журнал попадают путь и номер строки, совпавший
  текст маскируется.

Причина: смена провайдера или адреса не должна превращаться в вычистку кода, а комментарий «как было
раньше» ничего не объясняет тому, кто прежнего не видел, и устаревает в день, когда его не станет.

### 4. Приватный контекст и секреты — вне репозитория

Реальные значения — адреса серверов выдачи по контурам, координаты хранилища артефактов, параметры
подписи, доступы — лежат снаружи. `context/private` — ссылка на клиентский подкаталог внешнего
каталога приватного контекста, и она в `.gitignore`. В гите — только карта `context/README.md`
и шаблоны `*.example.*`.

- Перед задачей про адреса, публикацию, подпись или доступы прочитай нужный файл из
  `context/private/`. Файла нет — не выдумывай значения: назови, какого не хватает, и сошлись
  на шаблон.
- Секреты не читать без необходимости и никогда не печатать в вывод, логи, тексты ошибок и коммиты.
- Тесты приватного контекста не требуют: сборка в чистой копии зелёная.

## Требования к клиенту

`docs/requirements.md` — единственный список функциональности клиента: что он обязан уметь. Код
развивается по нему.

- **Состав.**
  - БТ-n — функциональные бизнес-требования, то есть что получает игрок.
  - БТ-n.m — технические подпункты: как это работает и чем проверяется.
  - Корнер-кейсы К-n и приоритеты между функциями собраны в отдельном разделе в конце, основной
    список ссылается на них. Пример — что показывает главная кнопка, если одновременно есть
    обновление игры и обновление клиента.
  - «На будущее» — только функции, которые запланировал владелец; они ещё не обязательны.
- **Только требования.** В документе нет истории, статусов реализации, обоснований и рассуждений,
  правило 3 действует и здесь. Пункт — одно требование, коротко, понятно и человеку, и агенту.
- **Меняет владелец.** Новое требование, его правка или удаление — только по решению владельца.
  Правка поведения клиента и правка документа идут одним merge request.
- **Подпункт закрывается кодом и тестом** по его формулировке; тест ссылается на номер подпункта.
  Номера не переиспользуются.
- **Контракт главнее.** Если требование расходится с контрактом, прав контракт (правило 1):
  требование правится вместе с контрактом.

## Тесты

Тесты держат поведение клиента: правка, которая его меняет, роняет тест, а перестройка кода без
смены поведения проходит на тех же тестах.

- **Сценарный тест на каждый флоу.** Тест проходит сценарий игрока через ядро целиком и проверяет
  итог: файлы в папке игры, сохранённое состояние, что увидел игрок, какие запросы ушли на сервер.
  Проверки внутренних вызовов итог не заменяют.
- **Тест меняется только вместе с поведением.** Пришлось поправить тест — значит, поменялось
  поведение: в том же merge request меняется требование, а решение за владельцем.
- **Сбой — тоже сценарий.** Флоу, который качает или пишет на диск, проверяется и на сбоях: обрыв
  сети, отмена, повторный запуск, выход из клиента посреди работы.
- **Ошибка исправляется с теста**, который на ней падает.
- **Тест должен уметь падать.** Новый тест проверяют поломкой: убрали поведение — тест красный.
  Тест, который нельзя уронить, ничего не охраняет.
- **Тест детерминирован.** Без сети, текущего времени и случайности без зерна, каждый в своём
  временном каталоге. Поэтому всё внешнее — время, HTTP, процессы, реестр, вопросы игроку — ядро
  получает снаружи, а тест подменяет.
- **Что автотест не проверит** — реестр, права, замену exe, трей, вид окна — проверяется запуском
  на Windows; не запускалось — так и пиши в merge request.
- Тест назван по поведению и условию, а не по методу; один сценарий — один тест.

## Переход с клиента, уже установленного у игроков

Переход — отдельный план, в `docs/requirements.md` он не входит. Импорт состояния установленного
клиента (`launcher.mv.db`) держит два правила:

- **Перенос один раз и целиком.** Переносятся признак установки, линия, применённые варианты,
  отметки скачанных пакетов и настройки. Флаг в той базе — само наличие строки, а не её значение.
  Импорт не затирает того, что игрок поменял после.
- **Очистка только по импорту.** Однократная очистка папки игры срабатывает только по состоянию,
  импортированному у установленного клиента, и никогда — по флагу, который записал сам этот клиент.

## Ветки: одна сессия — одна ветка

Основная ветка — `master`, прямые вливания в неё закрыты. **До первой правки** определи состояние
рабочей копии:

- чистая копия на основной ветке — заведи ветку сессии;
- ветка незакрытого merge request, который ты продолжаешь, — работай в ней; устаревание лечится
  перебазированием в своей сессии, чужую отставшую ветку мимоходом не трогай;
- чужая или устаревшая ветка (своих коммитов нет, имя не про задачу) — заведи новую;
- грязная копия — покажи список изменённых файлов и спроси: перенести в ветку сессии, оставить или
  отложить. Чужую незакоммиченную работу не присваивай.

```bash
git fetch origin
git switch -c <задача-или-слаг> origin/master
```

- `git fetch origin` — первая команда: без неё `origin/master` — срез на конец прошлой сессии,
  и отставание всплывёт конфликтом на мерже — позже всего и не у того, кто его создал. База — всегда
  `origin/master`, не локальный `master`.
- Имя — идентификатор задачи целиком; сессия шире одной задачи — короткий слаг темы. Одна ветка —
  один merge request; смержили — ветка и её ворктри удаляются, возврат к теме — новой веткой.
- Свою ветку агент коммитит и пушит сам, без спроса: дальше его ветки ошибка не уходит. История
  не переписывается — ни `--amend`, ни `--force`; ошибка исправляется следующим коммитом. `--force`,
  удаление веток на сервере и пуш в `master` — решение человека.
- Merge request открывает человек, агент — только по прямой просьбе. Пуш сессионной ветки прогон
  не заводит: конвейер идёт на merge request, на `master` и по ручному запуску.
- Ворктри — сосед основной копии (`../mfr-launcher-ng-<задача>`): `context/private` — относительная
  ссылка, на другой глубине она пуста, а в свежем ворктри её создают руками. Убирается вместе с веткой.

## Параллельная работа агентов

- **Параллельно — только по разным файлам.** Независимые задачи по разным проектам решения ведутся
  одновременно. Правки в одних и тех же файлах параллельно не ведутся: такие задачи разводят по
  проектам или выносят в отдельный ворктри.
- **Только последовательно и одним агентом:** `contract/`, `Directory.Build.props`,
  `Directory.Packages.props`, `context/`, `docs/requirements.md`. Конфликт в них дороже выигрыша.
- **Ворктри без приватного контекста.** В свежем ворктри нет ссылки `context/private`, поэтому задачи
  про адреса, публикацию и подпись там не ведутся: агент не увидит значений и начнёт их выдумывать.

## Версия и выпуск

Версия — `<Version>` в `Directory.Build.props`, единственный источник: из неё берутся версия сборки,
подпись в окне настроек и id записи дистрибутива. Выпуск конвейера — появление в `master` версии
без суффикса `-SNAPSHOT`, для которой ещё нет метки `vX.Y.Z`: конвейер публикует неизменяемый exe
и последним заданием ставит метку, коммитов он не делает; метка на другом коммите — отказ. Ручные
метки `v*` закрыты защитой: упавшую метку ставит ручной прогон `master` на том же коммите.

**До первой правки кода** прочитай `<Version>`. С суффиксом `-SNAPSHOT` — цикл открыт, версию
не трогай. Без суффикса — выпуск закрыт, писать поверх него нельзя (задание `version` отвергнет
ветку): цикл открывает правка в той же ветке, что и работа.

Номер и суффикс решает владелец — спрашивай одним ходом вместе с прочими развилками сессии. Второй
октет — новое или изменённое поведение, третий — исправление в пределах выпущенного, первый — только
отдельным решением: заниженный номер обещает совместимость, которой нет. Суффикс самовольно не
снимается никогда: нет прямого ответа владельца — ставится снапшот.

Снапшот и сборки merge request вшивают адреса тестового контура, выпуск с `master` — боевого;
на запуске их меняет `launcher.json` рядом с exe.

Выдача игрокам — отдельный от выпуска шаг, и делает его человек: загружает exe из пакета проекта
через админку, регистрация заводит запись закрытой, перед открытием объект скачивают из обоих
регионов раздачи и сверяют по хешу с собранным — апдейтер установленного клиента хеш не проверяет.
Агент дистрибутив не загружает и не открывает.

## Структура

| Каталог | Назначение |
|---|---|
| `contract/` | Дословные копии контракта основного репозитория и `SOURCE` с меткой |
| `Mfr.Protocol` | Классы из `contract/*.proto`, DTO ответов API |
| `Mfr.Core` | Домен: задачи установки, обновления и проверки, сеть, состояние в SQLite, импорт состояния установленного клиента, конфигурации движков |
| `Mfr.Launcher` | Avalonia: окна, модели представления, скин. Тонкий слой |
| `Mfr.*.Tests` | Тесты; контрактные — в `Mfr.Protocol.Tests` |
| `Mfr.Smoke` | Живые пробы против сервера: адрес и пути аргументами, в конвейер не входит |
| `deploy/gitlab-ci/` | Конвейер: свои скрипты и дословные копии общих из основного репозитория |
| `deploy/docker/` | Образ заданий с SDK и прогретым кешем пакетов |
| `docs/` | Требования к клиенту (`requirements.md`), решения клиента (`decisions.md`) и задачи |
| `context/` | Приватный контекст: в гите только карта и шаблоны |

## Сборка и проверка

```bash
deploy/gitlab-ci/build-dotnet.sh             # то же, что задание build:dotnet: restore, build, test, publish
dotnet build Mfr.Launcher.slnx -c Release -warnaserror
dotnet test Mfr.Launcher.slnx -c Release
dotnet publish Mfr.Launcher -c Release       # один exe под win-x64
deploy/gitlab-ci/sync-from-main.sh <метка>   # обновить копии контракта и общих скриптов
```

- Параметры публикации — win-x64, самодостаточный одиночный exe — живут в `Mfr.Launcher.csproj`;
  скрипты флагов не дублируют и файл не переименовывают. Артефакт — `Mfr.Launcher.exe`, имя файла
  у игрока задаёт апдейтер, а самообновление пишет поверх собственного пути процесса.
- Готово, когда изменённое поведение закрыто тестом, а сборка и тесты зелёные той же командой,
  что в конвейере.
- Конвейер: логика в `deploy/gitlab-ci/*.sh`, любое падение воспроизводится локально той же командой.
  Merge request блокируют `version`, `leak-scan`, `build:dotnet` и `contract`; код 3 у `contract` —
  только предупреждение: в основном репозитории вышла метка новее закреплённой. На `master`
  добавляются `publish:launcher` и `publish:tag`; `image:ci` — ручное.
- Сборка в конвейере идёт без сети: пакеты берутся из прогретого кеша образа заданий. Версии
  пакетов — только в `Directory.Packages.props`, в csproj лишь `Include`; `packages.lock.json`
  коммитятся, SDK закреплён в `global.json`, источник пакетов — `nuget.config`.
- Добавил или изменил пакет, lock-файл или SDK — merge request будет красным на `build:dotnet`
  с именем недостающего пакета, пока человек не пересоберёт образ (`image:ci`). Скажи об этом
  и спроси согласия; сам образ не пересобирай и не публикуй.

## Соглашения по коду

- Тестируемое живёт в `Mfr.Core`: статус главной кнопки и его приоритеты, сравнение версий, правила
  линий и импорта. `Mfr.Launcher` только показывает и передаёт команды.
- Ожидаемые исходы — типизированные результаты и закрытые иерархии, разбор без ветки по умолчанию.
  `catch (Exception)` в ядре не глотает ошибку и не ловит отмену: `OperationCanceledException`
  проходит насквозь, таймаут HTTP отличается от отмены по токену.
- В `Mfr.Core` — `ConfigureAwait(false)`; хеширование, копирование и удаление не идут на UI-потоке.
- Пути манифеста — с `/`, сравнение с локальными — после нормализации; пути на диске — через
  `Path.Combine`: тесты идут на Linux.
- Данные с сервера — внешние: путь из манифеста или схемы проверяется до записи и не выводит её
  за пределы папки игры.
- Комментарий объясняет «почему», по-русски; TODO — только со ссылкой на задачу; закомментированного
  кода нет. Сообщения коммитов — по-русски.
- Статус и история — в задачах и `docs/decisions.md`, не в коде, не здесь и не в `docs/requirements.md`.

## Грабли

- **Avalonia.** `Classes` — через пробел. `ControlTheme` живёт в `Styles.Resources`. В шаблонах
  `ContentPresenter` нужен явный `Content="{TemplateBinding Content}"`; `TemplateBinding` умеет
  `Mode=TwoWay`. В шаблоне ComboBox нет ToggleButton: клики ловит сам контрол, попап открывает
  `IsOpen="{TemplateBinding IsDropDownOpen}"`.
- **Привязки рефлексивные** (`AvaloniaUseCompiledBindingsByDefault=false`): ошибка в пути видна только
  при запуске. Картинку из файла грузи явно в `Bitmap`, на неявное превращение строки не рассчитывай.
- **Потоки.** Окно из фоновой задачи — через `Dispatcher.UIThread.InvokeAsync`. Диалоги экрана
  настроек — от видимого окна: главное в этот момент скрыто, иначе падение. Прогресс из воркеров —
  `Dispatcher.Post` с троттлингом ~10/с, иначе интерфейс перестаёт отвечать на клики.
- **Исключение команды** из `AsyncRelayCommand` уходит в диспетчер; без обработчика
  `Dispatcher.UIThread.UnhandledException` лаунчер закрывается. Ошибку показываем, процесс живёт.
- **Опрос.** Периодические проверки запускаются один раз на процесс и останавливаются при уходе
  в офлайн; повторная инициализация (новый `Opened` окна, тик опроса, конец задачи) таймеров не множит.
- **Версия.** SDK дописывает к `AssemblyInformationalVersion` хвост `+<sha>`; он отключён
  (`IncludeSourceRevisionInInformationalVersion=false`), иначе версия не совпадёт с id записи.
  Интерфейс читает именно `AssemblyInformationalVersion`: в `AssemblyName.Version` суффикса нет.
- **Пути с `[FR]`** в шелле — glob-класс: всегда в кавычках.

## Диагностика

- Рядом с exe: `task-trace.log` (ротация 1 МБ) — статусы, старт и финиш задач; `crash.log` —
  необработанные исключения; `launcher.json` — переопределение адресов (шаблон `launcher.example.json`).
- Состояние клиента — `launcher.db` (SQLite); `launcher.mv.db` — состояние установленного клиента,
  только чтение.
